Display name: Kallskär Nuclear Power Plant. Use ASCII "Kallskar" in code, instance names and DataStore keys.

====================================================================================================
WHAT THIS PROJECT IS
====================================================================================================
A multiplayer Roblox simulator of a fictional Swedish nuclear power plant, Kallskär Nuclear Power
Plant, unit K1. Its reactor is the SFR-1000: a 2,380 MWt pool-type sodium-cooled fast reactor with
MOX fuel, feeding two 500 MWe turbine-generators through three secondary sodium loops. Loop 1 feeds
turbine A, loop 3 feeds turbine B, and loop 2 feeds both through splitter valves.

Players staff several separate control rooms and have to talk to each other and walk between rooms to
keep the plant running. The goal is realism that stays fun: hard but fair, never AFK-able on manual,
never soloable from one room.

Developer: Aqua (Roblox / Luau). Nothing has been built yet. These files describe the design only.

====================================================================================================
HOW TO USE THESE FILES
====================================================================================================
1. Read this file, then 01 (project brief and game rules), then 02 (design history and rationale).
2. Treat the spec files 10 to 16 as the source of truth for every number, setpoint, rule and name.

HARD CONSTRAINTS FOR THE CODE
====================================================================================================
- Roblox, Luau. The server runs the simulation authoritatively; clients render and send commands.
- Simulate numbers, never moving fluid geometry. Performance is an explicit design goal (file 01).
- Fixed-step loops: 10 Hz fast physics, 1 Hz slow processes, replication at 5 Hz and 1 Hz (file 16).
- Reactor physics is real-time 3D multigroup space-time kinetics: hexagonal-Z nodal diffusion, improved
  quasi-static method, coupled per assembly to thermal-hydraulics (file 11 section 3.7, file 16
  section 14.2). The amplitude uses the prompt-jump form; explicit integration at 10 Hz blows up.
  The heavy shape solve must be time-sliced across frames. Point kinetics stays as fallback and check.
- Modular: one ModuleScript per system behind a common interface (init, step, getState, applyCommand,
  faults), so failure end states, scenarios and later features plug in without touching the core loop.
- One shared config module holds every spec number; the simulation, guide boards and tests read it.
- Controls: any player within reach of a panel may use it, seated or standing. Critical controls also
  require minimum playtime. Every action is logged with player name and time.
- Plant condition persists per private server with an owner reset; public servers start fresh.

====================================================================================================

- Scenario director: required; first rules and costs in file 15, section 13.1.

PROJECT BRIEF AND GAME RULES
Kallskär Nuclear Power Plant, SFR-1000. Rev A2.

====================================================================================================
1. WHAT THE DEVELOPER WANTS
====================================================================================================
- Realism the developer can be proud of, while staying fun. Inspiration: the Roblox game RBWR, loved
  partly because it is arcadey. The developer loves Roblox reactor games in general.
- Explicitly NOT like the Roblox game Oakridge. That game is laggy, and its reactor can be run solo
  from the main control room without ever leaving it.
- Dynamic play, as the developer defines it: constantly moving between controls, and constantly
  contacting the other control rooms.
- Not AFK-able on manual. The only acceptable exceptions are systems that are naturally stable while
  the reactor is stable, such as the deaerator and the condenser hotwell.
- Multiple control rooms. RBWR already has an MCR, TCR, FWP CR, CCR and EDG CR, and that is a lot to
  manage; this game goes further on purpose.
- A difficult grid dispatcher as the main difficulty lever.
- The developer chose the sodium fast reactor because it is harder to control and the stakes are higher.

====================================================================================================
2. DESIGN PRINCIPLES
====================================================================================================
Hard but fair, never hard and confusing.
- Readability tools: sequence-of-events log with timestamps and player names; first-out annunciators;
  post-event debrief screen with trends of power, flow, core outlet temperature and reactivity
  balance; training mode with the dispatcher switched off.

Workload comes from real behaviour. Real reactors are designed to be stable, so never fake instability.
Four realistic sources:
  1. Integrating processes: levels and inventories drift whenever inflow and outflow differ.
  2. Slow drifts: burnup, fouling, impurity build-up, demand, seawater temperature.
  3. Coupling: correcting one desk's variable disturbs another desk's.
  4. Genuine instabilities where physics has them, such as density-wave oscillation in once-through
     evaporators at low flow.

Automatic controllers are deliberately worse than a good crew (spec file 14, section 9.4): slower,
less efficient, blind to faults. Small servers survive on auto; full crews do better.

Anti-solo through realism: some actions only exist in the field (breakers, dampers, diesel starts,
freeze valves, screen washing), and rooms are far enough apart that walking takes time (file 14,
sections 10.1 and 10.3).

Fatigue and damage are partly hidden. Players see transient counts and temperature rates, not exact
damage numbers. On persistent servers a reckless crew leaves a worse plant for the next session.

The dispatcher's tension is grid pressure against plant damage. A crew can follow safe ramp rates and
take grid penalties, ramp too fast and build hidden fatigue, or use turbine bypass and throw energy
away. Refusing an instruction for a valid plant reason is rewarded, not punished. Difficulty is mostly
the dispatcher's personality.

====================================================================================================
3. MULTIPLAYER RULES (developer decisions)
====================================================================================================
Access
- Any player can press any control, whether seated or not.
- The server checks that the player is within reach of the panel (about 10 studs, tuning). Proximity
  is what keeps the anti-solo design working.

Critical controls
- Manual reactor trip, secondary shutdown system trip, turbine trips, opening 400 kV and 11 kV
  breakers, loop drain, steam generator section dump and plant mode changes require a minimum total
  playtime on the game. Suggested 3 hours; not final.

Trips and vote-kick
- If a player trips the plant, other players are free to vote-kick them, which bans them from that
  server.
- Proposed safeguard, not yet confirmed by the developer: the vote only opens when the server finds
  no genuine trip condition, P1 alarm or approaching setpoint at the moment of the trip, so a justified
  trip never gets someone kicked. Majority of the other players, minimum 3 voters.

Accountability
- Every control action is logged with player name and time and shown in the sequence-of-events log.

Sessions
- No shifts and no handovers. Players stay wherever they like, for as long as they like.
- Wherever the spec says "shift", read "session". The session report appears at the end of each grid
  day and whenever a player asks for it.

Learning
- Guide boards dotted around the plant: desk cards, alarm response cards, field guides and room maps
  (file 14, section 10.8). Guides read numbers from the shared config so they never go stale.

Persistence
- Plant condition persists per private server. The private server owner can reset it: typed
  confirmation, then a 60-second countdown announced to the whole server. Public servers start fresh.

Seasons
- The season follows the real-world calendar by default; a private server owner can pin a season.

====================================================================================================
4. INTERFACE
====================================================================================================
- Hybrid control rooms in the style of Temelín: the original 1988 analog panels plus plant computer
  screens added in the 2009 modernisation.
- Rule: anything that changes plant state is a physical control on a panel. Screens show, sort and
  trend; they never replace a control.
- Each room has a large mimic board. Colour convention for mimic lines and system identity:
  core and primary sodium red; secondary sodium and steam generators orange; steam and water blue;
  electrical and grid violet; control and crew teal; damage and scenarios amber; implementation slate.
- Natural screen content: the 331-position core thermocouple map, trends, alarm list, event log.
- Stays physical: the 30 rod controls, pump switches, breakers, trip buttons, synchroscope.
- Control room language is English. Site signage and PA are Swedish first, English second.

====================================================================================================
5. PERFORMANCE APPROACH
====================================================================================================
- Reactor physics must be ultra realistic: real-time 3D multigroup space-time kinetics coupled per
  assembly to thermal-hydraulics (file 11, section 3.7). The rest of the plant is lumped-parameter.
- Heavy solves are time-sliced across frames so the server never stalls.
- Replicate state values only; clients interpolate gauges between updates.
- A high MWe rating costs nothing because it is just a number. Building size and part count are what
  cost performance: full-scale Superphénix-sized buildings are how Oakridge-style lag happens. Build
  modular buildings and use streaming.
- Alarm logic runs on the server; clients receive state changes only.

====================================================================================================
6. DEFERRED BY THE DEVELOPER
====================================================================================================
- Build order.
- Failure end states (keep modular hooks).
- Playable refuelling (timed wait for now).
- Panel-level instrument and tag lists.

DESIGN HISTORY AND RATIONALE
Kallskär Nuclear Power Plant, SFR-1000. Rev A2.
Why the plant is the way it is. Read this before proposing design changes.

====================================================================================================
1. HOW THE REACTOR TYPE WAS CHOSEN
====================================================================================================
Ruled out, with reasons:
- RBMK: excluded by the developer from the start.
- AGR: the developer's friends call AGRs inefficient and massive. Correction made at the time: AGRs
  reach about 41% efficiency against about 33% for a PWR; their real problems were cost, size and
  reliability. Still rejected as too slow and forgiving for this game.
- ESBWR, pebble-bed and other high-temperature gas reactors: passively stable, so boring to operate.
- EBR-II and other metal-fuelled fast reactors: too forgiving. EBR-II famously shut itself down safely
  in its 1986 loss-of-flow tests.
- BN-800 as the base design: more automated, and less documentation available in English.
- Natrium: its molten-salt heat storage would remove the dispatcher tension. Kept as a possible later
  unlockable upgrade.
- Joyo, FFTF: test reactors with no turbine side.
Shortlisted fallbacks: PWR first, then BWR.
Chosen: sodium-cooled fast reactor, because it is more of a pain to control and the stakes are higher.

Reactor comparisons discussed along the way (BWR against PWR controls and transients, a CANDU system
breakdown, BWR and PWR startup sequences) don't apply to this design and are not carried forward.

====================================================================================================
2. CONFIGURATION DECISIONS AND WHY
====================================================================================================
- Fictional plant mixing the strengths of documented sodium fast reactors worldwide.
- Pool type. Loop type was noted as the maximum-pain option (radioactive primary sodium outside the
  vessel, faster transients) but not chosen.
- Oxide (MOX) fuel, because metal fuel is too forgiving.
- BN-600 layout: several loops, a pool, and sectional steam generators whose evaporator, superheater
  and reheater modules can be isolated at power. Preferred over Superphénix's single large
  once-through steam generator per loop, because isolating sections creates decisions.
- Superphénix-like scale and grid presence.
- Three loops into two turbines, the developer's own idea: loop 1 to turbine A, loop 3 to turbine B,
  loop 2 to both through splitter valves. Each turbine is rated for 1.5 loops' worth of steam.
- 2 x 500 MWe = 1,000 MWe, the developer's proposal. Big enough to matter to a grid controller, small
  enough not to feel sluggish. Plant size alone doesn't set sluggishness: response comes from sodium
  mass relative to power (0.53 t/MWt here, close to BN-600, versus about 1.1 for Superphénix) and
  from ramp limits in %/min, which give a bigger plant more MW per minute.
- A single turbine trip (500 MW) is survivable for the grid; a reactor trip (1,000 MW) forces the
  dispatcher to call reserves. Faults come in natural tiers.
- Splitter valves sit on the steam generator desk, the developer's proposal and realistic: the
  splitters set loop 2's steam pressure and flow, which that desk owns. Turbine desks only get
  repeaters and must call the SG desk. The turbines can still shift the split indirectly through
  header pressure. Throttling costs output, so good crews run the splitters wide open and coordinate.
- Each splitter branch has a check valve so header A and header B can't feed each other. Losing loop
  3 drops header B pressure, loop 2 steam rushes to B, the A-side check valve closes, and turbine A
  loses half of loop 2 unless someone intervenes.
- Turbine minimum stable load of 30% came from that analysis.
- Sodium plenum above the core (a BN-800 idea) is not fitted, so sodium voiding stays strongly
  positive. It was offered as a difficulty option and declined.
- Phased-build lore explains the asymmetry: loop 1 and turbine A first, loop 3 and turbine B second,
  loop 2 last as a shared loop (file 10, section 1.5).

====================================================================================================
3. HOW THE NUMBERS WERE DERIVED
====================================================================================================
- Heat balance computed with IAPWS-IF97 steam tables and the Fink-Leibowitz sodium correlations.
- The first idealised steam cycle gave 44% gross efficiency, higher than any real sodium plant. Turbine
  losses were then set realistically, giving 41.9% on steam generator heat and 42.0% on reactor power,
  between BN-600 (about 41%) and BN-800 (about 42%). That fixed the reactor at 2,380 MWt, slightly
  below the earlier rough estimate of 2,400 to 2,500 MWt.
- Loop 2 reheater split: the splitter moves main steam between turbines, but reheater capacity is
  fixed by pipework, so the loss-of-loop-3 decision became numeric. Best answer: send 60 to 70% of
  loop 2 to turbine B, losing about 3 MWe. Keeping 50/50 leaves B at 33%, just above its 30% minimum
  load. Sending 100% to B loses 22 MWe and runs both reheat lines out of specification.
- The fatigue model charges damage from real wall temperature differences rather than from ramp rate,
  so a well-coordinated crew can ramp faster without extra damage. Procedural ramp limits still apply.
- Seawater: cold Bothnian Sea water allows up to about 514 MWe gross per unit in winter. Below about
  5 °C intake temperature, one cooling water pump per unit beats two on net output.
- File 20 holds the full list of assumptions and the script.

====================================================================================================
4. DEVELOPER DECISIONS ON THE OPEN QUESTIONS
====================================================================================================
OD-1 Names and setting: reactor unit SFR-1000; station Kallskär Nuclear Power Plant. The developer
     proposed the name, chose "Power Plant" over "Power Station", chose a Nordic setting and asked for
     the details to be decided for them: Hälsingland coast of Sweden, unit K1.
OD-2 Sodium plenum: none.
OD-3 Neutron channels between source and power range: log wide-range, the realistic modern option.
OD-4 Loop 2 reheaters split 4 sections to turbine A and 4 to turbine B: yes.
OD-5 Default control mode: reactor leads.
OD-6 DRACS air dampers on loss of power: fail as-is, because motor-driven dampers can't move without
     power. Lore note: some passive designs avoid this with dampers that fall open on power loss, or
     no dampers at all, so Kallskär's are the older and cheaper choice.
OD-7 Primary pump trip at power: automatic runback RB-2.
OD-8 Refuelling outage: a timed wait for now.
OD-9 Persistence: per private server, and the owner can reset it.

Physics fidelity: the developer wants ultra-realistic reactor physics and first asked for "full 3D
two-group kinetics". Two-group diffusion is the light-water reactor simulator standard; a fast
reactor has almost no thermal neutrons, so the realistic equivalent is multigroup. Chosen: real-time
3D multigroup space-time kinetics (hexagonal-Z nodal diffusion, improved quasi-static method),
coupled per assembly to thermal-hydraulics. The earlier lumped physics values became validation
targets. Point kinetics stays as a fallback and a development cross-check.

Game design answers:
- Griefing: controls are free for everyone; tripping the plant lets others vote-kick with a server
  ban; minimum playtime for critical controls; buttons work without sitting.
- Learning curve: guide boards dotted around the plant.
- Handovers: none, because players come and go as they please.
- Scenario director: definitely needed.
- Failure consequences: later; the codebase must be modular so they can be added.
- Interface: hybrid control room like Temelín.
- Build order: later.

====================================================================================================
5. REAL EVENTS USED AS SCENARIO BASES
====================================================================================================
- PFR, Dounreay, 1987: a superheater tube leak spread to dozens of neighbouring tubes. Lesson:
  hesitation escalates.
- Phénix, 1989-90: four unexplained negative reactivity trips. The detective scenario.
- Fermi 1, 1966: a loose zirconium plate blocked coolant flow and partially melted fuel. The single
  hot thermocouple mystery.
- Monju, 1995: secondary sodium leak from a thermocouple well broken by flow-induced vibration.
- Superphénix, 1987: sodium leak from the fuel storage drum.
- BN-600: around two dozen sodium leaks over its life.
- Oskarshamn 3, 2013: jellyfish clogged the cooling water intake.
- Malmö, 2003: a geomagnetic storm caused a blackout.
- Forsmark 1, 2006: a switchyard fault and voltage transient disabled two of four emergency power
  trains, with some control room indications lost.

====================================================================================================
6. PUBLIC REFERENCES WORTH KNOWING
====================================================================================================
CANTEACH (CANDU training material), NRC Westinghouse PWR training manuals, IAEA fast reactor benchmark
reports, the IPFM report on fast reactor history (BN-600 and others), public EBR-II material.

ranges for BN-600, BN-800, Superphénix, PFR and EFR. It is not a licensing-grade design and doesn't
need to be.

1.1 Plant at a glance
---------------------
(Parameter / Value)
Station            : Kallskär Nuclear Power Plant, unit K1, Hälsingland coast, Sweden
Reactor            : SFR-1000: pool-type sodium-cooled fast reactor, MOX fuel
Thermal power      : 2,380 MWt
Gross output       : 1,000 MWe at the 5.0 kPa rating point (2 × 500 MWe); up to ≈ 1,028 MWe with
                     cold winter seawater
Net output         : ≈ 935 MWe (house load ≈ 65 MWe: main feed pumps 19.6, primary pumps 10.3,
                     secondary pumps 6.2, circulating water 14.8, everything else ≈ 14)
Gross efficiency   : 42.0%
Primary circuit    : 1,250 t sodium, 3 pumps, 6 IHXs, core 375 → 550 °C, 10,694 kg/s
Secondary circuit  : 3 loops, 3,112 kg/s each, 320 → 520 °C, ≈ 400 t sodium each
Steam generators   : 3 × 8 sections (evaporator, superheater, reheater), 99.5 MWt per section
Steam at SG outlet : 14.0 MPa, 505 °C; reheat 2.6 MPa, 505 °C; feedwater 240 °C
Main steam flow    : 291.7 kg/s per loop; 437.5 kg/s per turbine
Turbines           : 2 × HP + IP + 2 LP, 3,000 rpm, condenser 5.0 kPa, seawater cooled
Core               : 301 fuel assemblies, 30 rod positions, 1.0 m active height, ≈ 29 tHM
Kinetics           : Real-time 3D multigroup space-time kinetics (§3.7); β_eff 360 pcm; Λ 4.0 × 10⁻⁷
                     s; no xenon effect
Decay heat removal : 4 DRACS loops × 20 MWt, natural circulation
Emergency power    : 4 EDGs × 6.3 MW


1.2 Topology
------------
PLANT TOPOLOGY (text version of the diagram)

Reactor pool, primary sodium (1,250 t):
  Core 2,380 MWt -> hot pool 550 °C -> IHX 1A/1B, IHX 2A/2B, IHX 3A/3B -> cold pool 375 °C
  -> primary pumps PP1, PP2, PP3 -> diagrid -> core

Secondary sodium and main steam:
  Loop 1: IHX 1A/1B -> SG1 (8 sections) -> MSIV-1 -> Header A -> Turbine A (500 MWe)
  Loop 3: IHX 3A/3B -> SG3 (8 sections) -> MSIV-3 -> Header B -> Turbine B (500 MWe)
  Loop 2: IHX 2A/2B -> SG2 (8 sections) -> splitter
            branch A: CV-2A -> NRV-2A -> Header A
            branch B: CV-2B -> NRV-2B -> Header B

Reheat (cold reheat from each turbine's HP exhaust, hot reheat back to the same turbine's IP):
  Turbine A: reheater modules of SG1 sections 1-8 and SG2 sections 1-4
  Turbine B: reheater modules of SG3 sections 1-8 and SG2 sections 5-8

--------
(Item / Choice)
Location            : Kallskär, a former skerry on the Hälsingland coast of the Bothnian Sea,

Layout              : Reactor building on bedrock at the centre; SG buildings set apart for sodium
                      fire separation; turbine hall on the seaward side; switchyard inland; four EDG
                      buildings in separated divisions; backup control room on the landward side.
                      The headland is a natural map boundary
Time zone, daylight : CET/CEST; about 6 h of daylight in December, about 19 h in June


1.5 History
-----------

3.7 Core physics model
----------------------
Real-time 3D multigroup space-time kinetics: hexagonal-Z nodal diffusion, solved with the improved
quasi-static method and coupled assembly by assembly to the thermal-hydraulics. Every value in
§3.1–3.6, plus the peaking factors in §2.4, is a target the model must reproduce, not an input to
it.

NOTE: Why multigroup, not two-group. Two-group diffusion is the standard for light-water reactor
      simulators, where neutrons split cleanly into fast and thermal. A sodium fast reactor has
      almost no thermal neutrons, so its realistic equivalent is several fast energy groups.

What 3D adds in this core: a single rod moving tilts the flux and the thermocouple map; sodium
voiding adds reactivity at the core centre but removes it in the outer rings; a blocked assembly
changes local power; a gas bubble's reactivity depends on its path. Whole-core power response
changes little, because a fast core is tightly coupled. That is also why real sodium fast reactor
safety codes often still use point kinetics.

(Item / Specification)
Method                : Time-dependent multigroup neutron diffusion in hexagonal-Z geometry,
                        factorised by the improved quasi-static (IQS) method: flux = amplitude(t) ×
                        shape(r, E, t)
Energy groups         : 4 †, raised to 6 once performance allows. No upscattering in a fast
                        spectrum, so groups are solved in sequence from fastest to slowest
Delayed neutrons      : 6 precursor groups in every fuel node, constants from §3.1
Radial mesh           : One node per hexagonal position in rings 0–12 (469 positions: fuel, rods,
                        reflector); albedo boundary outside ring 12 †
Axial mesh            : 14 layers: 2 lower reflector, 10 fuel at 100 mm each, 2 upper plenum and
                        structure †
Size                  : 469 × 14 × 4 = 26,264 flux unknowns, plus precursors in the fuel nodes
Amplitude step        : Every 0.1 s: prompt-jump point kinetics (§14.2) using reactivity, β_eff and
                        Λ recomputed from the latest shape, weighted by the adjoint flux
Shape step            : Every 2 s at steady power; every 0.5 s while reactivity changes faster than
                        5 pcm/s, and for 60 s after any trip †. Time-sliced across frames
Steady state          : Eigenvalue (k_eff) and adjoint solve at server start, after a reset, and on
                        demand for the ECP calculator
Rods                  : The rod tip splits its node into absorber and sodium-follower fractions by
                        volume, with a cusping correction
Doppler               : Each fuel node's absorption and fission cross sections vary with ln(T_fuel)
                        of that node
Sodium density        : Each node's cross sections vary linearly with that node's sodium density, so
                        voiding happens node by node
Axial fuel expansion  : Fuel node height grows with fuel temperature; number densities fall to match
Radial expansion      : Diagrid (core inlet temperature) and load pads (core outlet temperature)
                        scale the assembly pitch; cross sections scale with density
Drivelines and vessel : Offsets added to every rod's effective position, with the §3.2 lags
Burnup                : Every fuel assembly tracks its own burnup; cross sections interpolate
                        between tabulated burnup points
Detectors             : PR quadrant chambers and SR and WR channels read weighted sums of peripheral
                        node fluxes, so quadrant tilt is physical
Thermocouple map      : Each outlet temperature comes from that assembly's own nodal power and flow
                        (§2.5)
Fallback              : Point kinetics with lumped feedback (§3.2) stays in the code as a low-load
                        fallback and as a cross-check during development

5.2 Sodium-water reaction protection
------------------------------------
* Micro
    Water leak rate: below 0.05 g/s
    Detected by: Hydrogen trend over grid-hours
* Small
    Water leak rate: 0.05–10 g/s
    Detected by: Section hydrogen meter within minutes
* Intermediate
    Water leak rate: 10 g/s – 2 kg/s
    Detected by: Acoustic leak detection, seconds
* Large
    Water leak rate: above 2 kg/s
    Detected by: Pressure rise and rupture discs, immediate

Hydrogen signal: a 1 g/s water leak adds +0.28 ppm at its section outlet meter and +0.036 ppm at the
loop outlet meter about 10 s later. Background is ≈ 0.06 ppm at 100% and 0.02 ppm at hot standby,
drifting ±0.01 ppm per grid day †.

Large leak, automatic sequence: rupture discs burst at 1.2 MPa, then separator tank, pump trip and
loop isolation, water side isolated in ≤ 5 s and blown down, nitrogen purge, sodium drained to the
dump tank, and reactor runback RB-1.

7.3 Bypass
----------
Two-stage bypass on each turbine: HP bypass from main steam to cold reheat, and LP bypass from hot
reheat to the condenser, each sized for 60% of turbine flow, quick-opening in ≤ 2 s on a turbine
trip, with desuperheating. The condenser absorbs 60% bypass indefinitely at design cooling water;
beyond that, condenser pressure rises about 1 kPa per extra 10% †. Bypass buys time. Every kilogram
through it is output thrown away.

House-load operation: when the grid separates, one unit can run back to the plant's own house load
(≈ 65 MWe) with the rest of its steam on bypass, while the other unit trips and the reactor runs
back. Getting it right keeps the plant off its diesels (S-28).

11.1 Instruction types
----------------------
* mFRR dispatch
    Example: "Plant to 800 MWe by 14:30"
    Rules: Deadline achievable at 1 %/min on Calm; needs 1.5–2 %/min on Winter Peak
* Reserve contract
    Example: "FCR-D up 25 MWe per unit from 06:00 to 22:00"
    Rules: Headroom must be in place before the window opens
* aFRR
    Example: Setpoint signal, ±20 MWe
    Rules: Follow continuously while active
* Emergency instruction
    Example: "Maximum generation now" or "Reduce 300 MWe within 10 min"
    Rules: Real time; can be refused with a valid code
* Reactive power
    Example: "Unit A to +150 MVAr"
    Rules: 2 min to comply
* Transfer-limit curtailment
    Example: "SE2 to SE3 limit reached: reduce 200 MWe"
    Rules: Common in spring floods and on windy nights; planned ones are announced a grid-hour ahead

Valid refusal codes, each checked against the simulation before it's accepted: runback in progress;
SG section or loop isolated; LCO in force; reheat load limit reached; bypass above 40%; fatigue
review open (§12).


11.2 Frequency model
--------------------
f = 50 + x, with dx = −(x / τ) dt + σ √(2/τ) dW and τ = 90 s.

* Calm
    σ: 0.03 Hz
    Loss events: 1 per 60 min
    Instruction rate: 1 per 40 min; never stacked
* Standard
    σ: 0.05 Hz
    Loss events: 1 per 40 min
    Instruction rate: 1 per 25 min; emergency 1 per 2 h
* Winter Peak
    σ: 0.07 Hz
    Loss events: 1 per 25 min
    Instruction rate: 1 per 15 min; instructions arrive mid-fault; reactive requests
* Blackout Recovery
    σ: ±0.5 Hz swings
    Loss events: –
    Instruction rate: Islanded restart with block loads of 50–150 MWe

Loss event shape: nadir −0.2 to −0.45 Hz reached in 8–12 s, recovery time constant 120 s. Expected
plant response is the sum of whichever reserve contracts are active (§8.4): FCR-N proportional
inside 49.9–50.1 Hz, FCR-D up below 49.9 Hz, FCR-D down above 50.1 Hz.


11.3 Scoring
------------
(Item / Rule)
Dispatch error            : Integral of max(0, abs(MW − target) − 10) after the deadline, in MW·min
Frequency response        : How closely actual ΔMW tracked expected ΔMW
Penalties                 : Reactor trip; turbine trip; LCO breach; ramp above limit without
                            approval
Refusals                  : Valid refusals cost nothing; invalid ones cost the same as a missed
                            instruction
Hidden until end of shift : Fatigue usage added during the shift (§12.1)

12. DAMAGE AND DEGRADATION MODEL
====================================================================================================

12.1 Thermal fatigue
--------------------
Each monitored component has a wall temperature that chases its fluid: dT_w/dt = (T_fluid − T_w) /
τ_w, with τ_w = L² / (2α) and α ≈ 4 × 10⁻⁶ m²/s for steel. The stress proxy is abs(T_fluid − T_w).
Count half-cycles between turning points of that value, ignore ranges below 10 K, and charge D = 0.5
× (range / ΔT_ref)³ / N_ref per half-cycle.

What this does to play: slow, well-coordinated changes create tiny wall differences and cost almost
nothing, while trips and sloppy coordination cost a lot. A crew that holds P/Q and the
feed-to-sodium ratio tight can ramp faster than a sloppy crew without extra damage. The procedural
ramp limit still applies either way.

* Upper internals above core
    Fluid temperature: Mixed core outlet
    Wall: 40 mm
    τ_w: 200 s
    ΔT_ref: 150 K
    N_ref †: 400
    Failure it unlocks: Lost thermocouples; striping cracks
* IHX upper tubesheet
    Fluid temperature: Hot pool
    Wall: 100 mm
    τ_w: 1,250 s
    ΔT_ref: 120 K
    N_ref †: 500
    Failure it unlocks: IHX tube leak (S-21)
* SG evaporator tube bank
    Fluid temperature: Feed inlet vs sodium
    Wall: Tube and shell
    τ_w: 30 s
    ΔT_ref: 120 K
    N_ref †: 800
    Failure it unlocks: Micro leak (S-01)
* SG sodium inlet header
    Fluid temperature: SG sodium inlet
    Wall: 60 mm
    τ_w: 450 s
    ΔT_ref: 150 K
    N_ref †: 400
    Failure it unlocks: Sodium leak at weld
* Secondary hot leg thermowells and tees
    Fluid temperature: IHX outlet
    Wall: 25 mm
    τ_w: 80 s
    ΔT_ref: 150 K
    N_ref †: 600
    Failure it unlocks: Monju-type leak (S-11)
* Turbine HP and IP rotors
    Fluid temperature: Steam vs rotor metal
    Wall: –
    τ_w: 1,800 s
    ΔT_ref: 100 K
    N_ref †: 1,000
    Failure it unlocks: Vibration, derate
* Diagrid
    Fluid temperature: Core inlet
    Wall: 80 mm
    τ_w: 800 s
    ΔT_ref: 80 K
    N_ref †: 600
    Failure it unlocks: Flow distribution anomaly

Failure hazard per grid day for a component with usage U: λ = 0.002 × e^(6U) †. That is a rate, not a probability: at
U = 0.5 it is 0.04 per grid day, so about 4 % of components fail in a grid day; at U = 1 it is 0.807 per
grid day, which is about 55 %. Thermal striping: adjacent assembly outlets more than 40
K apart, held, add upper-internals damage at 1/5,000 per minute †.


12.2 Fuel
---------
(Mechanism / Model †)
Cladding creep above 650 °C midwall
    dD/dt = e^((T − 650) / 25) / 100 grid hours; failure at D = 1
Random failure                     : 2 × 10⁻⁵ per assembly per grid day × (burnup / 50 GWd/t)² ×
                                     overpower multiplier
Gas leaker                         : Cover gas Xe-133 and krypton rise over grid-hours; DND stays
                                     quiet
Open failure                       : DND rises. Left above 30 %FP for more than 8 grid-hours,
                                     fuel-sodium reaction swells the pin and threatens neighbours
Failed fuel location               : Reduce to ≤ 30 %FP; scan samples one group of 7 assemblies
                                     every 2 min


12.3 Sodium systems
-------------------
(Mechanism / Model †)
Cold trap loading                  : Impurity ingress 0.2 kg per grid day at power, 1 kg per fuel
                                     handling campaign; capacity 150 kg; trap ΔP proportional to
                                     loading²; plugging temperature rises 2 K per 10% loading above
                                     70%
Trace heating failures             : 1 per 2,000 zone-hours real: 60% open circuit, 30% stuck on,
                                     10% thermocouple failure
Drained line cooling with heater off
    DN50 from 200 °C to freezing in ≈ 40 min; DN900 in ≈ 20 h
Thawing a frozen line              : Heat from the free end only. Heating the middle first ruptures
                                     the pipe, because sodium expands 2.5% on melting


12.4 SG tube leak growth
------------------------
(Stage / Model †)
Micro, below 0.05 g/s  : Self-wastage doubles the leak every 2–6 grid-hours
Small, 0.05–10 g/s     : Jet wastage penetrates a neighbouring tube in 10–30 min at 1 g/s, 1–3 min
                         at 10 g/s. Each new failure adds a leak of the same size, which is the PFR
                         1987 cascade
Intermediate and large : Protection sequence in §5.2

What players learn to read: a real leak shows at its section meter first, and the loop outlet meter
follows about 10 s later at an eighth of the size. A failing meter steps or spikes on its own.
Background drift moves every section together.

13.1 Scenario director
----------------------
The director decides what goes wrong and when. It never cheats: every fault it starts is a real
initiating event in the simulation, and everything after that is physics and crew.

(Input / Used for)
Crew            : Occupied desks and players on site in the last 5 min
Performance     : Recent P/Q, steam temperature and dispatch errors; trips; how the last fault went
Plant state     : Mode, power, isolated equipment, fatigue usage, active LCOs
Season and time : Season (§1.7), grid clock hour, weather
Difficulty      : Calm, Standard, Winter Peak, Blackout Recovery

(Rule / Detail †)
Intensity budget : Each scenario has a cost: minor 1, moderate 3, major 8. The director earns 1
                   point per 10 min on Standard, scaled ×0.5 with 1–3 players, ×1 with 4–8, ×1.5
                   with 9 or more
Spacing          : At least 8 min between director-started faults; never a new one while a major
                   fault is unresolved
Crew fit         : Only pick faults whose first actions land on occupied desks, or on auto
                   controllers that can cope
Eligibility      : Every scenario has prerequisites: season, mode, power, equipment state. Frazil
                   ice needs winter and open water; S-04 needs loop 2 running
Escalation       : A mishandled fault can grow into its poor-crew outcome. That growth is physics
                   and costs no budget
Recovery         : After a reactor trip, no new faults until the plant is stable in Mode 3 or back
                   above 30%
Ageing           : High fatigue usage (§12.1) raises the weight of that component's own failure
                   scenarios
Admin            : Private server owners can disable scenarios, force one, or change the budget rate

Cost classes †: minor S-01, S-06, S-10, S-12, S-13, S-14, S-17, S-23, S-24, S-26; moderate S-03,
S-05, S-07, S-08, S-11, S-19, S-20, S-21, S-22, S-25; major S-02, S-04, S-09, S-15, S-16, S-18,
S-27, S-28.

14. SIMULATION IMPLEMENTATION IN ROBLOX
====================================================================================================

14.1 Tick structure
-------------------
The server is authoritative, running a fixed-step accumulator on Heartbeat.

* Fast
    Rate: 10 Hz
    Contents: Kinetic amplitude, fuel and cladding, pools, IHXs, SG sections, turbines, pumps,
      valves, protection logic
* Shape
    Rate: Every 0.5–2 s, time-sliced
    Contents: 3D multigroup flux shape and precursors (§14.2)
* Slow
    Rate: 1 Hz
    Contents: Trace heating, cold traps, chemistry, fatigue counting, dispatcher, hydrogen
* Replication
    Rate: 5 Hz fast gauges; 1 Hz slow gauges and core map
    Contents: UnreliableRemoteEvent for gauges; RemoteEvent for alarms and events

Pack the 331 core-map temperatures into a buffer as u16 at 0.05 K resolution: 662 bytes per update.


14.2 Space-time kinetics in real time
-------------------------------------
The improved quasi-static method splits the flux into an amplitude that changes fast and a shape
that changes slowly, so each part runs only as often as it needs to (§3.7).

Amplitude, every 0.1 s. Λ is 4 × 10⁻⁷ s, so explicit integration at 10 Hz is hopeless. Use the
prompt-jump form with scaled precursors s_i = λ_i Λ C_i, which removes Λ entirely. Reactivity, β_eff
and Λ come from the latest shape, weighted by the adjoint flux.

    -- amplitude, once per 0.1 s tick: n is taken linear across the step, which keeps the
    -- growth rate right at high reactivity (holding n at its old value runs 11% slow at 0.8 beta
    -- and 22% slow at 0.9 beta; a fully implicit form errs the same amount the other way)
    local num, den = q, BETA - rho
    for i = 1, 6 do
      local x = lambda[i] * dt
      local e = math.exp(-x)
      local w = (1 - e) - (1 - e - x * e) / x
      num = num + s[i] * e + beta[i] * n * (1 - e - w)
      den = den - beta[i] * w
    end
    local n1 = num / den
    for i = 1, 6 do
      local x = lambda[i] * dt
      local e = math.exp(-x)
      local w = (1 - e) - (1 - e - x * e) / x
      s[i] = s[i] * e + beta[i] * (n * (1 - e - w) + n1 * w)
    end
    n = n1

Initialise at steady state with s[i] = beta[i]  n. The form holds while ρ stays below about 0.9β.
Above that, flag a prompt-critical excursion and hand over to a scripted core-damage event rather
than integrating through it.

Shape, every 0.5–2 s. One implicit time step of the multigroup diffusion equations over the whole
mesh, renormalised so shape and amplitude stay consistent.

(Step / Detail)
Group order       : Fastest group first, one group at a time. A fast spectrum has no upscattering,
                    so each group sees a source that is already known
Inner solver      : Red-black successive over-relaxation, warm-started from the previous shape; 4–8
                    sweeps per group †
Outer loop        : Repeat the group pass until the fission source changes by less than 10⁻⁴,
                    usually 2–3 passes with a warm start
Precursors        : Updated per node with the same exponential form as the amplitude
Time slicing      : Runs in a coroutine that yields once the frame has used 4 ms †; the amplitude
                    keeps power moving in the meantime
Cost              : About 26,000 unknowns; a warm-started shape step is a few hundred thousand node
                    updates. Put --!native at the top of the solver module
Development check : For a uniform perturbation, the 3D amplitude must match the point-kinetics
                    fallback


14.3 Thermal nodes
------------------
Update every lumped node with T = T_eq + (T − T_eq) × e^(−dt/τ), taking T_eq and τ from current
flows. It's stable at any time step. Treat the 0.19 s coolant rise through the core as algebraic,
and model pipe and pool transport delays as ring buffers with fractional interpolation.

(Block / Suggested states)
Fuel                : Every fuel assembly × 10 axial layers, with fuel and cladding temperature per
                      layer feeding its own neutronics node: 301 × 10 × 2 states. Sodium temperature
                      per layer is algebraic
Pools               : Hot pool 2; cold pool 1
IHXs                : 6 × 3
Steam generators    : 24 sections × 3 modules × 2 nodes
Secondary transport : 6 delay lines
Turbines            : 2 × rotor speed and metal temperature
Feed trains         : 2 × 5
Totals              : ≈ 6,300 thermal states, mostly fuel pins; ≈ 150 valves; ≈ 180 heater zones; ≈
                      600 alarm points


14.4 Keeping it multiplayer
---------------------------
Any player within reach of a panel can use its controls, seated or standing; the server checks
distance, not seats (§10.7). Critical controls also check playtime. Local-only actions (§10.3) are
ProximityPrompts with hold durations. Room phones connect desks, and the dispatcher line rings only
at the shift supervisor console.


14.5 Performance guardrails
---------------------------
Simulate numbers, not parts; there is no moving fluid geometry anywhere. Build the turbine hall and
SG building as modular, streamed instances. Run alarm logic on the server and send clients state
changes only.


14.6 Persistence and reset
--------------------------
Plant condition persists per private server (OD-9). Between sessions it keeps the cycle day and
burnup, fatigue usage for every component, failed, isolated and drained equipment, cold trap
loading, LCO clocks and the sequence-of-events log. Public servers always start fresh.

The private server owner can reset from a settings panel. A reset needs typed confirmation, then
runs a 60-second countdown announced to everyone on the server, and returns the plant to hot standby
at beginning of cycle with every component as new †. Key the save on game.PrivateServerId, check
game.PrivateServerOwnerId before allowing a reset, and version the save format so later spec changes
can migrate old plants.


14.7 Modules
------------
Keep every system in its own ModuleScript behind the same interface, so failure end states,
scenarios and later features plug in without touching the core loop: init(config), step(dt),
getState(), applyCommand(player, command), plus a faults table each module registers with the
scenario director. Every number in this spec lives in one shared config module that the simulation,
guide boards and tests all read.

import math
from iapws import IAPWS97 as W97
def S(**k):
    if 'T' in k: k['T']+=273.15
    return W97(**k)
hf=lambda P:S(P=P,x=0).h
ts=lambda P:S(P=P,x=0).T-273.15
def rho(T): t=1-(T+273.15)/2503.7; return 219+275.32*t+511.58*t**.5
def cp(T): K=T+273.15; return 1.6582-8.479e-4*K+4.4541e-7*K*K-2992.6/K/K
def dh(a,b,n=100): d=(b-a)/n; return sum(cp(a+(i+.5)*d)*d for i in range(n))
def psat(T): K=T+273.15; return math.exp(11.9463-12633.73/K-.4672*math.log(K))
def kNa(T): K=T+273.15; return 124.67-.11381*K+5.5226e-5*K*K-1.1842e-8*K**3
def mu(T): K=T+273.15; return math.exp(-6.4406-.3958*math.log(K)+556.835/K)
def ex(h,P0,P1,eta):
    s=S(P=P0,h=h).s; return h-eta*(h-S(P=P1,s=s).h)
def cycle(Trh=500.0,Pc=0.005):
    h1=S(P=13.5,T=500).h
    h2=ex(h1,13.0,3.5,.84); h3=ex(h2,3.5,2.8,.84)
    h4=S(P=2.5,T=Trh).h
    h5=ex(h4,2.5,1.1,.88); h6=ex(h5,1.1,.55,.88)
    h7=ex(h6,.55,.2,.85); h8=ex(h7,.2,.08,.85); h9=ex(h8,.08,.03,.85); h10=ex(h9,.03,Pc,.85)
    T=3; hc=hf(Pc); hcp=hc+S(P=Pc,x=0).v*2.5e3/.8
    hL=[S(P=2.5,T=ts(P)-T).h for P in (.03,.08,.2,.55)]
    hda=hf(1.0); hfp=hda+S(P=1.0,x=0).v*16.5e3/.83
    hH6=S(P=17.5,T=ts(2.8)-T).h; hH7=S(P=17.5,T=ts(3.5)-T).h
    m7=(hH7-hH6)/(h2-hf(3.5))
    m6=((hH6-hfp)-m7*(hf(3.5)-hf(2.8)))/(h3-hf(2.8))
    mda=(hda-(m6+m7)*hf(2.8)-(1-m6-m7)*hL[3])/(h5-hL[3]); mc=1-mda-m6-m7
    m4=mc*(hL[3]-hL[2])/(h6-hf(.55))
    m3=(mc*(hL[2]-hL[1])-m4*(hf(.55)-hf(.2)))/(h7-hf(.2))
    m2=(mc*(hL[1]-hL[0])-(m3+m4)*(hf(.2)-hf(.08)))/(h8-hf(.08))
    m1=(mc*(hL[0]-hcp)-(m2+m3+m4)*(hf(.08)-hf(.03)))/(h9-hf(.03))
    mrh=1-m7-m6; mlp=mrh-mda-m4
    Wt=(h1-h2)+(1-m7)*(h2-h3)+mrh*(h4-h5)+(mrh-mda)*(h5-h6)+mlp*(h6-h7)+(mlp-m3)*(h7-h8)+(mlp-m3-m2)*(h8-h9)+(mlp-m3-m2-m1)*(h9-h10-35)
    hsg=S(P=14.0,T=505).h; hrho=S(P=2.6,T=505).h
    return dict(We=Wt*.978*.988,Qms=hsg-hH7,Qrh=mrh*(hrho-h3),mrh=mrh,h3=h3,T3=S(P=2.8,h=h3).T-273.15,
